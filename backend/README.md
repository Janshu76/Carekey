# CareLink backend

FastAPI backend for the CareLink Emergency Bridge demo. It uses SQLite by default and seeds ten synthetic patient records, two mock source systems, trusted contacts, consent settings, sample body-region conditions, and demo QR tokens.

> **Demo only:** all seeded patient information is synthetic. OTP delivery and responder login are mocked. Do not use this service for real medical records or production authentication.

## Run locally

From the repository root in PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r backend\requirements.txt
.\.venv\Scripts\python -m uvicorn backend.app.main:app --reload
```

Open the interactive API reference at `http://127.0.0.1:8000/docs`. Database setup and demo seeding happen when the API starts. `DATABASE_URL` can be set to a PostgreSQL SQLAlchemy URL such as `postgresql+psycopg://user:password@host:5432/carelink` for a deployed demo.

For PostgreSQL, install its driver with `.\.venv\Scripts\python -m pip install -r backend\requirements-postgres.txt`.

Run the backend test suite:

```powershell
.\.venv\Scripts\python -m pytest backend\tests -q
```

## Run with Docker Compose

From the repository root:

```powershell
docker compose up --build
```

The API listens on port `8000`. The Compose configuration is for local demonstration only.

## Demo authentication

Guardian OTP is generated by `POST /auth/otp/request`. In non-production mode the response contains `demo_code`; no SMS is sent. Verify it with `POST /auth/otp/verify` and use the returned bearer token for guardian routes. The first seeded guardian phone is `+91 98990 11223`.

Create a simulated responder session with `POST /auth/responder/login`, passing a responder `name` and `organization`. Use its bearer token to validate or scan a patient token. The demo login does not verify responder identity.

## API workflows

- **Guardian:** `GET /patients`, patient details, consent and review status, trusted contacts, access history, notifications, conditions, and admission prefill require a guardian bearer token. Patient-specific requests are scoped to the authenticated phone number.
- **Consent:** `POST /patients/{patient_id}/consents` changes field-level permission, tier, and expiry, and persists an immutable receipt retrievable at `/patients/{patient_id}/consent-receipts`. Supported fields are blood group, allergies, medications, conditions, contacts, injuries, and insurer.
- **QR token:** `POST /patients/{patient_id}/tokens` creates a random token with a maximum 24-hour TTL and optional single-use behavior. The raw secret is returned once; the database stores only its keyed digest. Tokens can be revoked by ID or secret.
- **Responder:** `POST /access/scan` validates token status, applies current consent, merges Hospital A and Clinic B, returns a FHIR-shaped Bundle and source/conflict metadata, writes a hash-linked audit entry, and queues a family alert. Break-glass access requires a reason and is logged distinctly.
- **Admission:** `GET /patients/{patient_id}/admission-prefill` returns only currently consented medical fields. `POST /admission` records an admitted status and queues a family notice; `GET /patients/{patient_id}/admissions` provides the guardian timeline. Insurer notice requires current insurer consent and contains no medical details.
- **Condition timeline:** guardians can view and add conditions, injuries, surgeries, or devices with a body-region label through `/patients/{patient_id}/conditions`.
- **Health:** `GET /health` is public.

Set `ENVIRONMENT=production`, `SECRET_KEY` to a strong random value, and `CORS_ORIGINS` to the exact deployed frontend origins before deployment. Production mode does not seed demo patients and disables the mock OTP and responder-login endpoints. HTTPS, real OTP delivery, durable audit anchoring, deployment secrets management, database migrations, and a production identity provider are still required before handling real patient data.
